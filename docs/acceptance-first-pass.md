# DMC3 — first bounded acceptance pass (Linux base)

**Status:** partial player acceptance and visual capture; most checklist items remain unverified. This is a correctness survey, **not** a Slice-vs-Frame benchmark or proof of completion. Keep original NSPs, stable build and game data untouched; do not publish generated executables, logs, saves or captures.

## Candidate and isolation

From this experimental checkout, run `./run-acceptance-audio7.sh`. This uses the existing `out-h264-ffmpeg-slice-audio7/base` executable with FFmpeg **Frame**, four threads, audible `audio7`, normal 60 Hz pacing, `KIRIKAE_STATS=1` (periodic summaries **and thread profiling**, not an uninstrumented benchmark), and no per-frame tracing or dumps. Frame is **provisional**, chosen to avoid an extra decoder comparison; the previous Slice and Frame sessions differed in route/duration and cannot rank performance. The first original build remains at `work/kirikae/out-base/base`, untouched.

The launcher uses a separate, **persistent** local save root at `work/dmc3-acceptance-saves`. It does **not** import an existing save or change default Kirikae saves. Restart with the **same launcher** when checking save/reload; if the necessary equipment or scene is inaccessible in a fresh save, record **not tested** rather than modifying the original save. A human must not overwrite their only progress. Logs are under `diagnostics/acceptance-<timestamp>-<pid>/runtime.log` in the experimental checkout. The log records technical observations, not whether the image or audio looked/sounded correct.

## One short path, not a full playthrough

1. **Title and controls:** navigate a few menu items, confirm/back and enter gameplay. Test one input device first. Observe readability, selection, sound and unwanted repeat/stuck inputs.
2. **Short combat:** move in different directions, use two available actions, pause and resume. Observe response, animation, music/effects, frame pacing and whether gameplay speed stays normal.
3. **Equipment:** open Guns/Equip/Devil Arms if available; navigate and switch one unlocked item if possible. Observe icons/previews, missing/black/corrupted models and whether the selected item is reflected back in play.
4. **Save/reload:** use a save opportunity if available, exit cleanly, launch the **same** acceptance script again, reload, and check progress and the item choice. If saving is unavailable at this point, mark it untested.
5. **One accessible cutscene:** observe image order, stability, continuous/synchronized audio and return to gameplay/menu without a stuck screen. Do not repeat earlier Slice-vs-Frame A/B solely for this pass.
6. **Exit:** close normally and note whether it exits without a crash. If any step cannot be reached quickly, stop and mark it untested; do not force a 15-minute target.

Use keyboard **or** controller for the first pass; the other input device remains untested until actually exercised. Do not claim other cutscenes, full-game completion, update 1.0.1 or Windows from this pass.

## Graphics format candidate (2026-10-30; experimental)

Root-cause evidence for Loading: dynamic GPU trace after the noisy frame identified a `BC3_UNORM_BLOCK` 256×128 sprite at guest address `0x24e574000`; the previous runtime reused an existing `BC7_UNORM_BLOCK` 256×256 Vulkan image at the same address, then uploaded **32768 bytes of BC3** into that BC7 image (`texture()` → `find_image()` in `textures.rs`). The baseline's mislabeled BC7 upload and the candidate's correctly labeled BC3 upload contain **byte-identical source data**; the candidate's source bytes decode to legible `NOW LOADING` art. The format mismatch—not the source art or final swapchain—is demonstrated for this sprite.

One isolated fix was made: reject reuse of a sampled image whose Vulkan format class differs from the requested texture, so the BC3 image is created separately. The protected original NSPs and stable/base executable were not changed. `out-graphics-format-audio7/base` is a separate candidate with the existing provisional FFmpeg Frame/audio7 settings. In an automated route, baseline Loading was a colored block, while the candidate showed readable `NOW LOADING` without that isolated block; **broad green striped frames still occurred during the subsequent cinematic transition**, so other rendering/video defects remain. The same scripted Customize→Equip route showed multicolor static in baseline (`diagnostics/equip-baseline-20261030-100627-68689/frames/frame006765.png`) and a coherent weapon-circle background in the candidate (`diagnostics/equip-candidate2-20261030-100329-67544/frames/frame006930.png`). These are visual tests, not performance benchmarks. The pause→Restart confirmation was reached and selected in a candidate route, but the reported glitch on a Mission 1 menu **after restart** was not reproduced/cleared; do not mark it fixed.

The single regression test and all **202** `kirikae-rt` library tests passed with FFmpeg enabled; release build and Xvfb first-frame smoke of `run-graphics-format-audio7.sh` passed. Xvfb uses readback because DRI3 is unavailable; it does not validate the user's real-display presentation or subjective fluency. A diagnostic-only visual trigger/trace was archived locally in `diagnostics/visual-probe-20261030.patch` and removed from the clean candidate source. Do not promote the entire experimental checkout; async NVDEC remains mixed into it but disabled and has a known deadlock risk.

Their session `diagnostics/graphics-format-20261030-103537-80763/runtime.log` ended with exit code 0, which does not establish a rendering cause. An automated Xvfb route selected pause→Restart, advanced three tutorial overlays, and reached the Mission 1 menu at `diagnostics/restart-menu-repro3-20261030-105007-87301/frames/frame011970.png`. Subsequent SIFT registration of the player's crop onto this frame produced a ~1.5× scale transform with **446/457 inlier matches**; across valid aligned pixels the mean absolute RGB-channel difference was **1.38/255**, and **98.3%** of pixels had all channels within 10 levels. Thus the crop does **not** establish a real-display-only artifact. It also does not establish whether the matching image is correct game art: compare against a known-good original-game menu at the same state, or ask the player to mark the faulty region on a full-frame screenshot, before changing presentation code. Xvfb readback versus real-swapchain remains a potential confounder, not a diagnosed cause. Keep the restart issue separate from the confirmed BC3 fix.

## Full-screen Mission 1 evidence (2026-10-30)

The player supplied an uncropped 1291×753 screenshot and confirmed the horizontal/flat lower strip is **not** original art; main Mission 1 illustration and lettering remain intact. Registered against the automated after-Restart frame using SIFT: **1685/1717** matched features were inliers, and across the overlapping area mean absolute RGB-channel difference was **0.326/255**, with **99.73%** of pixels within 10 levels per channel. Thus the **same defect is reproducible in the Xvfb route**, not exclusive to the player's swapchain. In a bounded paired run (`diagnostics/mission-menu-target-20261030-110528-97030/`), the 960×540 internal GPU target `239300000` already contained the banded lower panel before final display, while `261300000` matched the final frame exactly. This rules out a *presentation-only* explanation for the reproduced artifact; it does not identify the draw/texture responsible. GPU trace near frame 12000 showed the menu drawing BC3 sprites at guest addresses `25a3ba800`, `24ea46400`, and `24ea05400` onto an intermediate target; a source dump of `24ea05400` contained legible Mission Start/Customize text and a distressed strip, not the broad flat side bands. The other two sprites/draw geometry still need isolation. Do not patch presentation or guess a menu texture from this alone.

The player's **earlier first-visit Mission 1 screenshot** (`952476...` in native inputs) and new after-Restart full screenshot also register to one another with **2321/2334** feature inliers; their lower strips differ by mean **0.012/255** RGB-channel intensity after alignment (selection may differ outside the lower strip). The band is therefore **not specific to Restart**: it was present on the first Mission 1 menu as well, although the player first noticed it after restarting. A separate trace near frame 12000 shows menu draws using compressed textures at guest addresses `25a3ba800`, `24ea46400`, and `24ea05400`. Replacing only `24ea46400` with a solid test texture changed the blade/bright overlay, not the lower band, so it is not the panel source. The broad source of the band remains unidentified; no production code was changed for this symptom.
